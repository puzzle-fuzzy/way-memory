# Route data integrity and memory limits

The live route is built from the `poseTrack` array returned by the API. The web console does not generate or fall back to a demo route for the live session. `track` and `relativeTrack` remain diagnostic compatibility views.

## Coordinate contract

- `lat` is latitude in degrees, limited to `-90..90`.
- `lng` is longitude in degrees, limited to `-180..180`.
- The server sorts each incoming batch by Android's monotonic `deviceTimestampNs`. It also keeps a per-session high-water mark for Pose, relative motion, motion events, and GNSS route points: a later batch cannot append an older route timestamp. Such a sample remains in the bounded raw replay and increments `outOfOrderSampleCount`, but it is excluded from the primary route so the web client cannot render a time-reversed segment.
- The web projection treats longitude as east/west and latitude as north/south. It uses a local earth-radius projection in meters, so the two fields cannot be accidentally swapped without failing the visible bounds check.
- Each live `TrackPoint` carries its device timestamp. The dashboard shows point count, segment count, coordinate bounds, and dropped sample count below the visualization.
- `sampleCount` counts all accepted sensor samples. The `track` length counts only accepted samples that contain a latitude/longitude pair; accelerometer, gyroscope, and rotation-vector samples are not position points.
- Android samples carry a stable `sampleId`. The server keeps a bounded per-session seen-ID window (8,192 IDs) and ignores repeats, so a crash between WebSocket send and local cursor commit cannot duplicate route points or sensor counts. Legacy samples without an ID remain accepted but cannot receive this idempotency guarantee.
- `rawSampleCount` counts normalized samples accepted into the bounded replay ring. The `/api/sessions/:id/raw` endpoint exposes only the retained tail, never an unbounded history.
- `GET /api/sessions` is a compact history index: it returns counts and metadata with empty track arrays, not every retained Pose point. The dashboard fetches one selected session's full snapshot only when needed; `GET /api/sessions/:id?view=integrity` provides counts, latest points and closure metadata for health checks without transferring the full track.
- `sensorInventory` is the bounded capability snapshot sent at session start. It records the Android sensor string type, name, vendor metadata, range/resolution, timing/power/FIFO hints, reporting mode, wake-up/dynamic flags, the client-side `transportMaxHz` diagnostic budget, and whether listener registration succeeded; `sensorStats` remains the separate observed-sample count.
- If a dynamic sensor connects or disconnects after session start, the authenticated device sends a bounded `session.sensors` update. The server merges it by sensor type and ID, persists the snapshot, and publishes `session.updated`; a later `session.resume` carries the latest inventory again so the capability change is not lost across reconnect or server restart.
- Android also carries `Sensor.getId()` as `sensorId` in inventory entries and raw samples when the platform exposes it. The server validates it as a bounded non-negative integer and preserves it through the replay tail, so two physical sensors with the same Android type remain distinguishable without changing the aggregate sensor-stat key or increasing the retention limits.
- Android consumes every registered callback locally for sensor fusion and updates the live reading state on every callback. The persisted/uploaded diagnostic stream is deliberately bounded: motion/rotation sensors up to 50 Hz, gravity/magnetic sensors up to 20 Hz, pressure and fused Pose up to 10 Hz, and other discovered sensors up to 5 Hz. A motion event can bypass the Pose window. This keeps “all available sensors are considered” separate from “all hardware callbacks are stored forever.”
- The Android uploader persists a bounded app-private offline queue capped at 4,096 samples and 8 MiB. It drops the oldest samples after either hard limit and surfaces the drop count in the capture UI. A batch is removed only after the server replies with `samples.accepted`; a socket or process failure before that reply leaves the batch for replay. The active session ID is persisted too, so a process restart can attempt to resume the same server session. If the server grace window has expired, the client creates a new session and drains the retained samples there. Replayed batches retain their `sampleId`, and the server's bounded dedupe window makes this at-least-once transport duplicate-tolerant rather than silently lossy.
- The durable queue stores one JSON object per line, while the WebSocket `samples` field is an array of JSON objects. The uploader parses each queued line back into an object before sending; it must never send an array of JSON-encoded strings, because the server intentionally rejects non-object samples instead of guessing at a second encoding layer.
- `poseTrack` counts unified fused-pose points in local ENU meters. Each Pose includes source flags, accuracy, velocity, motion mode and stationary state. Source flags can include `step-pdr` for the bounded step-aided walking fallback, or `*-stale` when an external stream has stopped contributing fresh evidence.
- Raw samples may carry a bounded primitive `metadata` object. The Android ARCore adapter uses it to preserve `trackingState`, `confidence`, `failureReason`, and `trackingReset` through the durable queue and raw replay; the server rejects nested, oversized, or non-primitive metadata.
- ARCore lifecycle changes also produce low-frequency `arcore.visual-status` diagnostic samples with `available`, `active`, `trackingState`, `failureReason`, and a bounded human-readable detail. They never carry a Pose or alter fusion; they make unsupported devices, camera denial, pause, recovery, and tracking failure auditable in raw replay.
- Each Pose may carry a `frame`: `local-enu` for the unified route frame or `arcore-local` for raw session-local visual coordinates. Legacy payloads default to `local-enu`; Android promotes ARCore samples only after horizontal frame alignment.
- `latestPose`, `latestRelativePosition`, and live sensor snapshots never move backward when a delayed callback arrives. On service restart, the persisted route windows are sorted and their timestamp high-water marks are restored before new samples are accepted. When the Android process itself restarts inside the server grace window, the device seeds its local fusion engine from the resumed session's last `latestPose`; the first GNSS/pressure reference is continuity-preserving rather than a reset to `(0, 0, 0)`, and the resulting Pose carries `recovered-anchor` for auditability.
- `relativeTrack` counts legacy device-side sensor-fusion motion points. These are local meters from the session origin, not geographic coordinates; the web console uses them only when no unified Pose stream exists.

## Filtering and 3D data

- Malformed numbers, invalid coordinates, invalid timestamps, vectors containing non-finite values, and oversized sensor vectors are rejected.
- A location point within `0.5m` of the previous point during a `2s` window is treated as a duplicate.
- A location jump larger than the configured walking-speed/uncertainty envelope is dropped when the time gap is short. The count is exposed as `droppedSampleCount`.
- GNSS altitude is normalized relative to the first accepted GNSS altitude. Barometer altitude is normalized relative to the first accepted pressure reading. This is relative route height, not centimeter-level phone lifting; that requires a later inertial vertical-motion model.
- Android records the location provider with each geographic sample. Only an explicit GPS provider is allowed to establish or update the primary geographic route or GNSS fusion; network/passive fixes remain bounded diagnostic samples even when GPS is unavailable, so a coarse first fix cannot create a false route. The server repeats this provider gate instead of trusting the client.
- A non-GPS location sample cannot smuggle a fused `pose`, `relativePosition`, or `motionEvent` into derived route state; the complete sample stays available in raw replay, while the server ignores all co-packaged derived values for route state.
- Android route capture requires precise location permission. Approximate/network-only location can report kilometer-scale accuracy and must not be mistaken for a dense pedestrian track.
- Inertial relative motion is a short-term observation layer. Double integration of acceleration drifts, so it must later be corrected by GNSS, visual-inertial tracking, landmarks, or manual annotations before navigation use.
- A closure is reported as `open`, `candidate`, or `closed`. When aligned visual metric evidence provides `loop-closure`, raw `poseTrack` remains immutable and the server creates a separate corrected Pose track; the web console never silently overwrites raw measurements.
- Repeated route observations are not concatenated by array order. The first stopped observation is the geographic reference; later observations use a monotonic nearest-reference match with a 25 m per-point gate. A candidate must match at least two distinct reference points and cover at least 50% of its GNSS points, with an average residual no greater than 25 m, before it can update the bounded reference `track`. The API requires three observations and two successful repeat alignments before publishing a route as `verified`.
- A `navigation` session is accepted only for an owner-scoped `verified` route. Each accepted GNSS point is projected to the nearest reference segment in local meters and updates bounded progress/remaining-distance/off-route state; it never treats the point array index as distance and it never reuses a learning session's local ENU frame as a navigation frame.
- The closure correction is timestamp-based and three-dimensional. It is distributed from the first pose to the visual return pose, then held constant for later poses; the correction metadata is included in the persisted session snapshot, so post-closure points and service restarts remain in the same corrected frame.
- The closure anchor and cumulative travelled distance are also persisted as bounded session metadata. They are not reconstructed from the last 1,200 Pose points, so trimming the live Pose window cannot move the logical route origin.
- Pressure and IMU evidence can produce an `elevator-candidate` event. It is not treated as a confirmed floor transition without additional visual or manual evidence.
- The web visualization is point-only and uses one canvas: every visible dot represents one accepted location sample, and the newest dot is highlighted. No interpolation or route line is drawn, so the display cannot invent movement between measurements. Height is projected into each point's screen position; the previous decorative floor grid and full ground-projection path are not part of the route. A canvas keeps the browser DOM size constant when a session contains many samples.

## Server-side bounds

The MVP is intentionally memory-bounded because sessions are currently in memory:

- 20 sessions maximum; stopped sessions are evicted oldest-first when capacity is needed.
- 100 persisted routes maximum; each route retains at most 50 observation summaries, 128 manual nodes, 500 reference location points, and 1,200 reference Pose points.
- 500 track points per session.
- 1,200 unified Pose points per session.
- 128 motion events per session.
- 1,024 normalized raw samples per session for short replay.
- 32 latest sensor types per session, with at most 16 values per sensor snapshot.
- 128 bounded sensor-stat entries per session, retaining counts and first/last device timestamps without retaining every raw value.
- 128 sensor-inventory entries per session.
- 500 samples per batch.
- 512 KiB maximum JSON request/WebSocket message budget.

The API never stores an unbounded raw sample history. It keeps bounded live aggregates, a recent Pose window, and a 1,024-sample replay tail. `bun run replay:session <session-id>` re-feeds that bounded raw tail into a fresh session for deterministic transport and route-integrity checks. On an enforced service, set both `WAY_MEMORY_DASHBOARD_TOKEN` (source read) and `WAY_MEMORY_DEVICE_TOKEN` (target write/stop); the script refuses to send either token to a non-HTTPS public endpoint. The API also snapshots sessions into SQLite at `WAY_MEMORY_DB_PATH` (default `.data/way-memory.sqlite`) every two seconds while active and immediately when stopped. At most 100 snapshots are retained, and an interrupted active session is recovered as `stopped` after restart. `WAY_MEMORY_RETENTION_DAYS` is the explicit data-retention window; local/test mode defaults to 30 days, while production refuses to start unless the operator sets an integer from 1 to 3,650 days. The same window applies to persisted routes, and the periodic cleanup removes expired stopped sessions/routes from memory and SQLite.
